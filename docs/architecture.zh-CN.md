# 架构说明：命令行 → 网页 → 回到命令行

这份文档解释这套东西是怎么转起来的。不讲代码细节，只讲逻辑。

---

## 一句话

**命令行才是这个系统本体，网页是它的一张脸。**

网页不是命令行的重写版，也不是另一套实现。它做两件事：把数据库读出来画成页面；以及在你点按钮的时候，**真的去启动一个命令行进程**，把它的输出原样播回给你看。

所以整件事是一个圈，起点和终点都是命令行。

---

## 三个角色

```
   ┌──────────────┐
   │   命令行     │   唯一会写数据的东西
   │   tracker    │   抓取、抽取、合并、评分，全在这里
   └──────┬───────┘
          │ 写
          ▼
   ┌──────────────┐
   │   数据库     │   一个 SQLite 文件
   │  tracker.db  │   项目 / 引用 / 事件 / 障碍
   └──────┬───────┘
          │ 只读
          ▼
   ┌──────────────┐
   │   控制台     │   网页，负责展示和触发
   │tracker serve │   自己不做任何判断
   └──────────────┘
```

三者的分工是硬性的：

- **命令行**负责一切会改变数据的事。抓网页、调模型、校验证据、合并冲突、算置信度。
- **数据库**是唯一的事实存放处。
- **控制台**只读它、只展示它。想改数据，控制台的办法也只有一个——去启动命令行。

---

## 那个圈：绕一圈回到原点

### 第一步：控制台怎么知道有哪些命令

控制台**没有**一份写死的命令清单。

它启动的时候去问命令行本身："你有哪些命令？每个命令有哪些参数？参数是什么类型？默认值是什么？帮助文字怎么写的？"命令行如实回答，控制台照着这份回答把表单画出来。

这样做的好处很直接：**命令行加了一个参数，网页下次启动就有了**，不需要有人记得去改两个地方。反过来说，网页上永远不会出现一个命令行不认识的按钮。

只有一件事是命令行答不上来的：**哪些命令要花钱**。这个没法从参数定义里看出来，所以是手写的一小张表（`sync`、`enrich`、`infer`、`search`、`ingest crawl` 这五个）。宁可手写，也不要靠猜——猜错的后果是有人手滑花掉一笔钱。

### 第二步：你点了"Run"，发生了什么

不是网页去"模拟"那条命令。是**真的起了一个进程**，和你在终端里敲的完全是同一个东西。

```
你在网页上填了参数，点 Run
        │
        ▼
控制台拿着命令名和参数，对照第一步那份清单逐项检查
   ├─ 命令不认识 → 拒绝
   ├─ 参数不认识 → 拒绝
   ├─ 类型不对   → 拒绝
   └─ 要花钱但没确认 → 拒绝
        │
        ▼
检查通过，拼出一个参数列表，启动进程
        │
        ▼
进程一边跑，一边把每一行输出推回浏览器
        │
        ▼
进程结束，输出存成一个文件，留在"Runs"页面里
```

有一点值得单独说：控制台拼的是**一个参数列表**，不是一行命令字符串。这个区别决定了安全性——列表里的每一项都是独立的一个参数，分号、反引号、`&&` 在里面就是普通字符，不会被当成命令来执行。系统里从头到尾没有任何一个地方把你输入的文字拼进命令行。

### 第三步：数据怎么回到页面

那个进程写完数据库就退出了。页面重新拉一次数据，画面就更新了。

圈就闭上了：

```
命令行定义了有哪些命令
        │
        ▼
控制台读出来，画成界面
        │
        ▼
你点一下
        │
        ▼
控制台启动命令行
        │
        ▼
命令行写数据库
        │
        ▼
控制台重新读数据库，刷新画面
        │
        └──────► 回到起点
```

---

## 一条铁律：网页不重新实现任何判断

这是整个设计里最重要的一条。

页面上所有需要"判断"的东西——一个项目走到哪一步了、某个数字凭什么、字段覆盖率算多少、哪些障碍压着多少产能——**全部由后端算好送过来**，网页只负责画。

为什么这么严格？因为一旦网页自己算一遍，就有了两套规则。两套规则一定会分叉，而且分叉的时候你不会收到任何通知——你只会看到网页和命令行说的不一样，然后不知道该信谁。

### 一个真实的例子

这个界面最早是从一份设计稿移植过来的。设计稿里有一段 JavaScript，自己算项目走到了哪一步，其中有一条规则是：

> 如果项目状态是"运营中"，那么"电力接入"这条轨道就算完成了。

听起来很合理。但后端的规则**明确拒绝**这样推断，理由是：先把楼盖起来、然后干等变电站，是这一轮建设周期里最常见的情况；一个盖好的空壳在等电，恰恰是这个工具最该暴露出来的信号。照设计稿那么推，这个信号会被无声地抹掉。

所以移植的时候，那段 JavaScript **被整段删掉了**，改成直接用后端算好的结果。

现在网页和命令行对同一个项目的判断是逐行一致的——不是因为两边都写对了，而是因为**只有一边在算**。

### 具体哪些是后端算的

| 页面上看到的 | 谁算的 |
|---|---|
| 五条轨道走到哪了、下一个信号是什么 | 后端 |
| 每个字段的证据等级、支持它的那句原话 | 后端 |
| 置信度 0–3 | 后端 |
| 字段覆盖率、以及分母该怎么取 | 后端 |
| 各类障碍后面压着多少产能 | 后端 |
| 排序、筛选、折叠展开 | 网页（这些是纯显示，不涉及判断） |

## 为什么读和写要分开

**读的那一侧，连数据库都是只读打开的。**

不是靠"我们小心一点不要写"，是数据库本身就不接受写入。展示逻辑里哪怕出了 bug，也只会报错，不会悄悄改掉一行数据。

**写的那一侧，同一时间只允许一个。**

SQLite 只接受一个写入者。两个任务同时跑，第二个会在跑到一半的时候崩掉——而那时候它已经花掉了模型调用的钱。所以控制台在启动新任务之前先看有没有正在跑的，有就直接拒绝并说明原因，而不是让你八篇文章之后才发现。

---

## 三道门

控制台能跑命令，所以有三道门挡着：

**第一道，地址。** 默认只监听本机。能访问本机就意味着已经坐在这台机器前面了，这时候再加一道密码没有意义。

**第二道，密码。** 一旦要放到公网上（比如开隧道），第一道门就失效了——隧道是从本机连出去的，看起来永远像本机访问。所以放公网的时候**必须**有密码，没设就直接拒绝启动。未登录时整个站点只有一个登录页，连前端代码都不给。

**第三道，确认。** 会花钱的那五个命令，必须把命令名手打一遍才会执行。这道门防的不是攻击者，是手滑。

---

## 和"导出成网页"的关系

系统里有两个网页，容易搞混：

| | `tracker export html` | `tracker serve` |
|---|---|---|
| 是什么 | 一个文件 | 一个服务器 |
| 数据 | 导出那一刻的快照 | 每次请求都重新读 |
| 能跑命令吗 | 不能 | 能 |
| 能发邮件吗 | 能，双击就开 | 不能 |
| 要装东西吗 | 不要，一个文件就够 | 要，得跑起来 |

两个都留着，因为用途不一样：一个是**给别人看的成品**，一个是**自己干活的工作台**。

## 一句话总结

网页没有夺走命令行的任何职责。它只是把命令行**读出来**画成界面，在你需要的时候**启动**它，然后把结果**读回来**给你看。

判断永远只有一处，写入永远只有一条路。
