## Feedback 1 — DC role model is missing → rows get counted multiple times

**What they said.** A data-center project has multiple real-world roles
(developer, owner, operator, buyer of compute). The same physical Stargate
Abilene campus shows up under OpenAI, Oracle, Crusoe and a "OpenAI/Oracle"
composite, and gets counted four times. They've seen this duplicate
counting across the list.

**What the code does today.** The `Project` table has **one flat
`company` field and one flat `customer` field** (`models.py:69–70`). There
is no `developer` / `owner` / `operator` / `buyer` distinction anywhere.
`dedup.py:234–244` builds a storage key from `(company, locality, state)`,
so:

- Crusoe row → `crusoe|city:abilene|TX`
- OpenAI row → `openai|city:abilene|TX`
- Oracle row → `oracle|city:abilene|TX`
- OpenAI/Oracle composite → `openai oracle|city:abilene|TX`

Four keys, one campus. The code *knows* this is wrong — `dedup.py:389–394`
literally documents it in the comment:

> "the Abilene Stargate campus was stored four times, as
> `crusoe|city:abilene|TX`, `openai|city:abilene|TX`,
> `oracle|city:abilene|TX` and `openai oracle|city:abilene|TX`."

`capex.py:suspected_duplicates()` (lines 329–369) **flags** the four-row
group. But `capex.py:rollup()` (lines 161–219) **never calls it** — every
row contributes its full `mw_planned` and `investment_usd` to its
customer bucket. The fix exists in human form (`tracker merge`); it just
isn't applied.

There's a **planned but unbuilt** multi-tenant attribution model in
`docs/plan-sources-and-customer-axis.md` (Step 2, line 311): a join table
`(project_id, customer, mw, share, basis, source_id)`. Not implemented.

**Confirmed by `tracker duplicates`** in the live DB:

```
Abilene, TX: #3 Crusoe vs #8 OpenAI/Oracle
Abilene, TX: #3 Crusoe vs #93 OpenAI
Abilene, TX: #3 Crusoe vs #121 Oracle
Abilene, TX: #8 OpenAI/Oracle vs #93 OpenAI
```

`tracker capex`'s own footer says "31 pair(s) of rows look like one campus
stored twice, holding 24,125 MW that is counted more than once above."

**What to do next.** Three layers, in order of cost:

1. **Cheap, today.** Run `tracker merge` for the obvious clusters. The
   code already supports it (`merge.py:70–138` physically collapses rows,
   moves citations and milestones, recomputes fields). Stargate Abilene
   should be one row.
2. **Cheap, ~half a day.** Stop `capex.py:rollup()` from double-counting
   *before* a human merges. The `suspected_duplicates()` output already
   gives the pairs. Change `rollup()` to skip rows that are members of a
   2+ duplicate group *when their `investment_usd` is a "scale" (e.g.
   >$50B for a single campus)*, and show a `double_counted_mw` line
   instead.
3. **The right thing, multi-day.** Build the attribution join table from
   the plan doc, then re-roll `capex.py` to count MW-by-share instead of
   MW-by-row.

## Feedback 2 — Rows with no evidence look "not started"

**What they said.** Some Stargate entries have no citation, no MW, no
investment — yet the system calls them `announced` ("not started").
That's wrong: a project can be `announced` while still going through
land acquisition, permitting, financing, design. The system collapses
all of those into a single `announced` state, so it cannot tell "just
announced" from "we have a site, we're filing permits" from "we
announced three years ago and never moved."

**What the code does today.** `vocab.py:22–37` defines exactly six
`phase` values: `announced`, `permitting`, `construction`, `operational`
plus two terminal (`paused`, `cancelled`). `models.py:111` enforces this
via a CHECK constraint.

So far so good — `permitting` exists. But the live data shows the
problem: `tracker list --phase announced --min-confidence 1` returned 62
rows, **29 of which have MW = "—" and investment = "—"** (single source,
often press release). They're `announced` because no `permit_approved`
milestone has fired yet, but the system can't tell whether the project
is at "press release last week" or "stuck for three years."

The **5 tracks** in `tracks.py:47–53` (`site_control`, `permits`,
`power`, `construction`, `commercial`) exist precisely to encode the
sub-state. A project's track state is **derived from `event` rows** at
read time, never stored as a column. So the data is there — `site_work`
milestone means we have a contractor; `permit_approved` means the city
signed off; `energized` means power is live — but the **capex rollup
filters by `phase`, not by track**, so a row with `phase=construction`
but a stalled `permits` track is treated the same as a row with all
five tracks green.

**What to do next.** Two options:

1. **Lighter.** When listing or rolling up, show the five-track
   progress bar per project alongside the phase. A `phase=announced` row
   with `site_control=land_acquired, permits=filed, power=queued` is a
   very different risk than one with all five tracks empty. The code
   already has `tracks.standing()` (`tracks.py:247–292`) ready.
2. **Heavier.** Add a `phase_basis` column that records *why* the
   project is in its current phase (which track reached which milestone),
   so the system can answer "this row is `permitting` because the
   power track stalled, not the site track."

## Feedback 3a — OpenAI investment is $3.2T (should be much less)

**What they said.** The OpenAI row in capex shows investment of $3,215B.
Even the most aggressive Stargate framing puts OpenAI's announced
spend at $500B–$1T over five years. $3.2T is too high by a factor of
3–6x.

**What the code does today.** The sum is exact arithmetic in
`capex.py:rollup()` at line 199:

```python
bucket.investment_usd += int(project.investment_usd or 0)
```

That is, **the raw `investment_usd` from every row in the database
attributed to OpenAI is summed with no normalization, no deduplication,
no per-MW sanity check, and no $/MW cap**.

Three drivers, in order of impact:

1. **No de-dup in rollup** (capex.py:169, 185–189). The four Abilene
   rows are attributed to four different customer keys
   (`crusoe`, `openai`, `oracle`, `openai oracle`) because
   `customer_key()` doesn't split the `OpenAI/Oracle` string (dedup.py:
   `company_key()` does not split on `/`). Each row's full
   `investment_usd` is added. Some of these rows carry the headline
   "$500B Stargate" figure; if the headline was filed four times, it
   gets counted four times.
2. **Composite customer strings are their own bucket** (capex.py:147–158).
   "OpenAI/Oracle" resolves to key `openai oracle` — neither OpenAI's
   bucket nor Oracle's bucket sees the $500B, but **the sum bucket**
   does, so it inflates. There is no rule that distributes multi-tenant
   investment across the tenants.
3. **No $/MW sanity check.** Even a single 1 GW campus quoted at
   $500B is an outlier (typical: $5–10B per GW for the building, $50B+
   only when GPU spend is included). A row carrying $400B for a
   1,167 MW Stargate Doña Ana project (id 170) passes the sum
   unchanged.

The $400B / $450B / $500B Stargate sub-campuses (Milam, Lordstown,
Shackelford, Doña Ana, Michigan — see the OpenAI list) are themselves
*parts of* the headline $500B Stargate program, not independent
investments. They are duplicate rows at the program level. Same
physical double-count as Feedback 1.

**What to do next.**

- Stop the bleeding: capex.py should cap `investment_usd` to
  `mw_planned × $/MW cap` with an opt-out flag, and refuse rows where
  the figure looks like a program total rather than a campus total.
- Audit each `$100B+` row by hand and confirm it is a campus, not a
  program, not a duplicate.
- After Feedback 1's attribution table exists, `capex.py` should sum
  by share, not by row.

## Feedback 3b — 2029 column is missing in capex year grid

**What they said.** Capex shows MW columns for 2026, 2027, 2028, 2030.
2029 is skipped. The likely cause is that some rows have a 2030 *target*
from a press release but no row has a 2029 *projection*, so the table
just omits 2029.

**What the code does today.** `capex.py:horizon()` at lines 222–227
returns the **sorted union of all years any project attributed to any
customer has**. A year column appears only if at least one row has
`expected_online.year == that_year`. So if no row is dated 2029 for
OpenAI, no 2029 column.

`rollup()` populates `mw_by_year` at lines 201–205 from rows that have
*both* `expected_online` *and* `mw_planned`:

```python
if project.expected_online and planned:
    year = project.expected_online.year
    bucket.mw_by_year[year] = bucket.mw_by_year.get(year, 0.0) + planned
```

A row dated 2029 but missing `mw_planned` is skipped. A row dated 2026
*for* a campus that everyone knows will ramp through 2028–2030 only
contributes to 2026.

There is **no interpolation, no S-curve, no "phased buildout"
inference**. Each row contributes its single year if and only if it has
both fields.

**What to do next.**

- Cheap, today: render the year grid as `range(min_year, max_year+1)`
  so missing years appear as zero columns. The 2029 column will be
  visible (empty), which is honest.
- Heavier: when a row has `expected_online` but no MW, infer the
  capacity ramp from the project's `mw_planned`, `first_announced`,
  and any cited milestones. `infer.py` has the
  scaffolding for this; it's the same problem as inferring the phase
  track progression.
- Heaviest: hold every project to a single `expected_online` and either
  trust the source, or refuse the row.

## Feedback 4 — Evidence chain has placeholder-as-evidence mistakes

**What they said.** They saw a citation that quoted a field, but the
field's value was a placeholder ("TBD", "—", "N/A", or a missing
value). The system shouldn't accept a placeholder as an evidence gate.

**What the code does today.** Two layers:

1. **URL placeholders are caught.** `confidence.py:86` defines
   `PLACEHOLDER_MARKER = "PLACEHOLDER"`. Lines 276–279 strip any source
   whose URL contains that marker from confidence scoring. So a URL
   like `https://example.com/PLACEHOLDER` cannot earn a `company_filing`
   weight to push confidence to 3.
2. **Field-value placeholders are NOT caught.** Strings like `"TBD"`,
   `"—"`, `"N/A"`, `"unknown"` written into `mw_planned` /
   `investment_usd` / `customer` are stored as literal string values
   and treated like any other claim. `logic.py:check_rules()` and
   `check_collisions()` don't filter them. If a row's `investment_usd`
   is the string `"TBD"`, `int(project.investment_usd or 0)` evaluates
   to `0` because of the `or 0` (so it's actually dropped from capex
   sums — but only because the type coercion fails, not because the
   system recognized it as a placeholder). If `investment_usd` is
   `None`, same outcome. The system is **silently forgiving** rather
   than **explicitly rejecting**.

There's also a quieter version: the `Source.quotes` column
(`models.py:159`) stores per-field verbatim sentences the evidence
gate verified. If a source has no `quotes` entry for a field it claims,
that field is in `unconfirmed_fields` (line 153). The confidence scorer
treats that as missing evidence. But the **rollup in capex.py reads
`project.investment_usd` directly** — it doesn't check whether that
field has a verified quote. So a `$500B` value with a `quotes={}` empty
on the source still sums fully.

**What to do next.** Two changes:

1. **Add a placeholder list to `vocab.py`.** A closed vocabulary of
   `{"TBD", "—", "N/A", "unknown", "?", "tba", "n/a"}` plus regex
   detection. Any field whose value matches is stored as `NULL` instead
   of the placeholder string, and a warning fires at ingest time. The
   evidence gate and capex rollup already treat `NULL` correctly.
2. **Make `capex.py:rollup()` reject fields without verified quotes.**
   A row's `investment_usd` should sum into capex only if at least one
   of its `Source.quotes` entries has a non-empty string for that
   field. Rows without verified quotes are dropped with a note in
   `tracker capex`'s footer.

The AI evidence-check your colleague suggested (`tracker review
--check-evidence`) could be a third layer that runs LLM judgement on
each citation's `quotes` to flag semantic mismatches. `logic.py:examine()`
is the scaffolding for this.

## Feedback 5 — Are we using US planning, permits, grid, and operator filings?

**What they said.** Where are the data coming from? Are we using US
planning / land-use / interconnection / utility filings, or only press
releases and operator announcements?

**What the code does today.** Documented in detail in
`docs/government-sources.md`. The short version:

- **4 bulk-discovery routes were tested, 4 failed:**
  Socrata (municipal open-data) — Loudoun/Prince William/Virginia/Arizona
  not on it; FERC eLibrary API 404s; Ohio/Virginia/Texas PUCs are
  WebForms scrapers; county RSS feeds returned zero on-topic items
  (177 articles scanned, 0 kept).
- **One route that pays is already wired and has not been run at
  scale:** `tracker ingest edgar --kind utility`. SEC EDGAR filings
  by utilities carry their large-load commitments and
  interconnection agreements. Verified live: 19 filings found, 17
  prepared, ~17 LLM calls. **Not run yet.**
- **One-off government documents work today.** `tracker ingest crawl
  --url <permits URL>` reads any URL; `classify_source_type` maps
  `.gov` / `.mil` to `source_type = "government_doc"` automatically.
  The capability exists; bulk discovery doesn't.

So the answer to your colleague's question: **the source class
"government_doc" exists, the source class "utility_filing" exists, and
the bulk ingest for both has been researched and is documented.** What
hasn't been done is the bulk ingest run at scale. The single biggest
unrun ingest is `tracker ingest edgar --kind utility`.

**What to do next.** Three actions in order of ROI:

1. **Run `tracker ingest edgar --kind utility`.** This is the
   highest-leverage government/grid source we have. It pulls from
   SEC EDGAR (government host, rate-limited not bot-blocked), covers
   utilities in the 6 states that hold 79% of tracked capacity
   (TX/CO/NM/OH/GA/VA), and is configured to use the right vocabulary
   ("large load", "interconnection agreement"). **This is the one
   that should run first.**
2. **Hand-pick 6–12 individual government documents** (Loudoun County
   rezoning applications, Virginia SCC dockets for Dominion, ERCOT
   large-load filings, Georgia PSC dockets for Georgia Power) and
   `tracker ingest crawl` each. This proves the government's-data
   claim with concrete citations without trying to build a bulk
   discovery layer.
3. **Operator filings**: hyperscaler 10-Ks and earnings transcripts
   (NVDA, MSFT, GOOGL, META, ORCL, AMZN, CRDO) carry capex commentary
   that the company itself attributes. These are not "government" but
   are the highest-credibility "buyer" source. `tracker ingest edgar
   --kind hyperscaler` is configured; not run at scale.

After these three runs, the source-mix in `tracker stats --by
source_type` should show non-zero counts for `government_doc`,
`utility_filing`, and `company_filing`, which is the audit trail your
colleague will look for.
